# YORK RG94A/BGEF：状态编码与验证范围

原始 25°C 报文已成功重放。随后采集了五种模式、COOL 23°C 下的四档风量，以及 COOL 最大风量下 17–30°C 的逐度温度，用于核对生成编码，均吻合。HEAT 和 28°C 的初次样本有异常，已分别补到完整双帧，原异常记录保留。特殊键的实录和物理观察见 `captures/york-button-catalog.json`；尚未将新采集按键全部通过 UNO 重放验证。

## 编码

常规开机状态使用 24-bit 数据。线上按最高字节先发送，每个字节后紧跟它的反码：

```text
状态 B2 3F C0 → 线上 B2 4D 3F C0 C0 3F
```

对于关闭 Follow Me、忽略遥控器温度传感器的常规状态，本项目用：

```text
code = 0xB21F00 | (fan << 13) | (temperature_code << 4) | (mode << 2)
```

- 模式位：制冷 0、除湿 1、自动 2、制热 3。
- 风速位：用户称“微风”的第一档 5、低 4、中 2、高 1；自动/除湿模式锁定为编码 0，用户确认这两个模式不能手动调风量。
- 摄氏温度 17–30°C 的 nibble 顺序：`0, 1, 3, 2, 6, 7, 5, 4, C, D, 9, 8, A, B`。
- 纯送风是特例：模式位 1，温度 nibble 为 E；没有设定温度。

这覆盖普通状态，不把关机、摆风、灯光、睡眠、Turbo、定时等特殊命令误解成温度状态。

用户将四档更正为“微风 → 低 → 中 → 高”。这四档已分别收到 `B2BF50 / B29F50 / B25F50 / B23F50`（COOL、23°C），均为完整双帧且逐字节反码正确。上游库将第一档的风速位 5 命名为 `kCoolixFanAuto`，本项目编码器、解析器和目录仍保留内部键 `auto`；它在可调风量模式下对应用户称为“微风”的第一档，在 AUTO/DRY 模式下则对应锁定的风速位 0。不能把库里的名称当作本机实际风量行为的证明，也没有测量四档风量。

## 扇叶短按：相对步进

编号 27–39 共 13 条捕获全部为 `0xB20FE0`，线上字节为 `B2 4D 0F F0 E0 1F`。每次仅一帧、99 项时序值，不能照普通状态附加第二帧。用户确认每次移动一档，12 次回到起始位置，并在最后多按了一次。

因此这一轮按键发的是相同的步进指令，不是 12 个绝对角度码。12 档循环是用户的实物观察，尚未测量各档角度。以后若在软件中维护相对位置，漏收命令、原遥控器操作或关机复位都可能使位置记录失准；仅凭步进码不能获知当前绝对角度。

之后一次长按采集中，编号 40 仍为完整 `B20FE0`，编号 41 为 15 项时序的无法分类片段。用户确认这是上下 Swing，长按也只移动一档。另一枚用户称为左右 Swing 的键发出双帧 `B5F5B2`，已采集两次；不能将通用库中名称相近的常量直接代入。

## 特殊按键

- LED 四次均为双帧 `B5F5A5`。用户观察到灯亮/灭与提示音有/无的全部四种组合，具体循环顺序未确认，不提供未经验证的绝对“灯开/灯关”语义。
- Turbo 两次均为双帧 `B5F5A2`，原遥控器对应关系确认，实际风量变化未单独报告。
- Sleep 第一次短按为三帧 `B2E003 + B2BFC0 + B2BFC0`，第二次为双帧 `B2BFC0`。其中状态是 COOL 25°C、风速位 5。这两个完整样本会改变相关状态，不能当作与温度无关的固定 Sleep 切换码。
- Sleep Silence 长按收到交替的双帧 `B5F5B6 / B5F5B7`，用户确认 Silence 图标出现/消失；首次独立长按的 `B5F5B6` 对应出现。重复批次比要求多一次，逐帧界面标签未单独记录，`B5F5B7` 作为关闭对应码的解释仍保留此证据边界。
- Follow Me ION 短按两次无接收记录，用户确认接收灯和屏幕都无变化；长按收到双帧 `B5F5A3`，空调长鸣。具体功能未确认，暂按物理按键命名，不宣称已实现温度跟随或负离子控制。
- 电源关机为双帧 `B27BE0`；开机样本为双帧 `B2BFC0`，即恢复 COOL 25°C、风速位 5。普通开机状态也可用状态编码器生成，不能将这个固定开机样本解释为恢复任意先前状态。

特殊键按用户确认的标签关联完整原始时序。`scripts/generate_replay_catalog.py` 生成 `CapturedButtons.h` 和 `captures/york-replay-index.json`，保留单帧、双帧、混合三帧及原始帧间隔；异常或按键标签未确认的记录不进入重放目录。

## 生成和发送

```sh
# 在项目根目录运行
python3 scripts/coolix_states.py state --mode cool --temperature 23 --fan low --sequence 1
python3 scripts/coolix_states.py state --mode fan --fan high --sequence 2
python3 scripts/coolix_states.py catalog --output captures/york-state-catalog.json
python3 scripts/generate_replay_catalog.py
python3 scripts/coolix_states.py button --name vertical-step --sequence 3
```

Python 工具只生成代码，不打开串口或发送。状态控制固件为 `sketches/ACStateControl/ACStateControl.ino`，串口 115200 baud：

```text
STATUS
SEND 1 B29F50
```

每条有效 `SEND` 指令只发送一个双帧按键报文；5 秒内不接受下一次发送，不会自动重试。序号必须大于本次启动已使用的序号。复位会清空序号状态，但上电不自动发送。发射结束后 D3 回到 LOW。

程序已扩展 `PRESS <sequence> <button-index>`，用于一次原始按键重放，共用上述序号和 5 秒间隔。发送前检查板上 `STATUS` 的 `catalog` 标识与 Python 命令输出的 `expected_catalog_tag` 相同，避免索引对应到旧固件中的其他样本。原始重放以原捕获帧数为准，不额外补重复帧。

当前控制固件保留 `CYCLE24 <sequence>` 实验指令：重放关机后由 UNO 等待约 1 秒，再生成 COOL 24°C 大风。它每次启动最多执行一次，不在 Web API 中暴露；普通命令仍保留 5 秒间隔。不要把这项特定实验当作常规开关机策略。

固件大小、原始重放和生成状态的实物观察集中在[验证范围](验证范围.md)，不在协议说明中维护动态“最新序号”或串口占用状态。

生成波形使用名义时序：引导 4692/4416µs，位 mark 552µs，0/1 space 为 552/1656µs，帧间 5244µs，载波设置 38kHz、占空比设置 30%。它与之前逐项重放的实录时序不同，需要单独验证。

## 判定依据

编码器测试对照真实遥控器的五种模式、四档风量、17–30°C 逐度样本，以及上游默认/送风状态；144 个组合检查了唯一性、范围、模式限制和编解码一致性。另检查异常样本不会被列为完整采集、用户称呼与协议风速位对应，以及单帧步进和混合三帧 Sleep 的完整重放生成。协议相关检查不代替空调实际响应；完整测试入口及数量见 README。

每次实物试验分别记录“串口发送完成”和“用户观察到的空调反应”。温度、模式、风速未能观察的部分保留未知，不因空调鸣响就全部标为通过。
